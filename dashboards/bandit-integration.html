Bandit Integration how ShopWorks data & thumbnails flow to Caspio & Box

Admin Dashboard

Bandit is the always-on Windows box on the shop LAN that carries ShopWorks data into Caspio. It is not a file-copy or a Box client — it runs small PowerShell agents on a schedule that read ShopWorks and POST to our proxy, which does every Caspio write and every Box upload. Living document — kept current whenever the bandit tasks or sync scripts change. Verified live 2026-07-21.

The one rule that bit us

Never run two write-heavy Caspio syncs at full speed at the same time. On 2026-07-17 the thumbnail-metadata sync and image sync ran concurrently and tripped Caspio's per-second rate limit (api-calls-rate) — even though the monthly Integrations meter was only 496K/500K. The monthly cap is soft (billed overage), not a hard block; the per-second burst limit is the real ceiling. It looked like an outage but recovered the instant the concurrency stopped.

Steady-state, not backfill — keep them from bursting together

These are gentle now (deltas of a few rows/images per run). The one guard: don't let the metadata + image syncs fire a large batch at the exact same second (that's the per-second-limit trap). Steady-state overlap is fine; a future bulk re-load should be staggered or done via CSV import.

Caspio quota: Box Sync now 4 h — APPLIED 2026-07-27

A $358 Caspio overage (689.8K calls against a 500K/period cap). Measured live on 2026-07-26 with the repaired meter: Shopworks_Thumbnail_Report was 48% of ALL Caspio traffic — 909 of 1,883 calls in a 4.3-hour window.

  1. ✅ Thumbnail Box Sync 20 min → every 4 hours (applied 2026-07-27, verified). Before it uploads anything, each run makes two full scans of the 27,613-row Shopworks_Thumbnail_Report (/thumbnails/uploaded-ids 27 pages + /thumbnails/all-ids 28 pages = 55 Caspio calls per run, fixed). The backfill is complete and steady state is ~5 changed thumbnails/day, so 72 runs/day was 3,960 calls/day — roughly 800 Caspio calls per image actually synced. Now 6 runs = 330/day, saving ~3,630/day (~$218/period).
    schtasks /Change /TN "\NWCA\Thumbnail Box Sync" /RI 240
    Why 4 h and not daily: the cost is fixed per run, so 72→6 runs already captures 92% of the saving and going all the way to once-daily adds only ~$16/period more — not worth a 24-hour worst case. Trade-off as set: a brand-new thumbnail reaches Box/the portal in up to ~4.5 h (4 h for the image sync + up to 30 min for the metadata sync to create its row first) instead of ~20 min.
  2. 🔴 OPEN — 4 oversized thumbnails can never sync (found 2026-07-27). upload-with-stub caps uploads at 20 MB (multer limits.fileSize, src/routes/thumbnails.js:18). Four files on the share are 21–28 MB and fail every single run, and because multer's LIMIT_FILE_SIZE is not caught they surface as an opaque HTTP 500 ("An unexpected error occurred") rather than "file too large". Worse, the agent still logs 0 still pending, because its counter treats an errored file as processed — so the log reads clean while four images are permanently stuck.
    106886_Copy of Warriors2.png · 100641_36971 ETC Tacoma (9 Year Sports Collage) (Final) A.png · 98671_35921Coob Scooter Adult FF FP copy.png · 78223_BE KIND (1).png
    The names ("Copy of", "(Final) A", "copy", "(1)") suggest full-resolution artwork accidentally saved into the thumbnails share rather than genuine thumbnails. Decide per-file: resize/remove them at source, or raise the cap — noting multer.memoryStorage() holds the whole file in dyno RAM, so a higher cap is a memory trade.
  3. Do NOT slow the Thumbnail Metadata Sync. Its delta read is an ODBC query against FileMaker — zero Caspio calls. In steady state the whole task costs ~48 calls/day, nearly all heartbeats on Sync_Heartbeats, with only ~6/day touching the thumbnail table. There is no money in it, and it is the record-creator the image sync depends on (upload-with-stub 404s RECORD_NOT_FOUND rather than creating a row, because Thumb_DesLocid_Design is UNIQUE NOT NULL). Slowing it would also break its overlap — see the trap below.
  4. Re-copy the three updated agent scripts from caspio-pricing-proxy/scripts/bandit-agent/ to C:\NWCA\odbc-sync\: sync-orders.ps1, sync-purchase-orders.ps1, sync-thumbnail-metadata.ps1.

⚠️ The overlap trap — do NOT "simplify" this back. Order Sync and PO Sync run every 15 min but shared a 30-min OverlapMinutes, so every changed row landed in multiple consecutive runs and the proxy PUTs unconditionally — each change written to Caspio several times. They now read their own OrdersOverlapMinutes (default 20).
The shared OverlapMinutes stays at 30 because Thumbnail Metadata Sync runs on a 30-minute cadence — lowering the shared key to 20 would open a 10-minute window in which modified rows are never seen again. Note if ($cfg.OrdersOverlapMinutes) is PowerShell-truthy, so a literal 0 in config.json silently means 20.

✅ Content dedupe (2026-07-29) — the overlap is now free, so stop trying to shorten it. ORDER_ODBC was measured at 55% of all Caspio calls on a fresh web dyno. sync-orders.ps1 now keeps a SHA-1 of exactly what it last sent per order in last-sent-orders.json and skips rows whose content is unchanged. Proven on bandit against live data: first run 2 to send, 0 unchanged → posted 2; immediately re-run inside the same overlap window, 0 to send, 2 unchanged → posted 0.
The overlap was NOT reduced — it is the clock-skew and long-transaction safety net, and the dedupe delivers the same saving without spending it. Two guards that must survive any edit: a capped run bypasses the dedupe entirely (state is not advanced on a cap and FETCH FIRST has no ORDER BY, so deduping there would post rows:[] and stamp a green heartbeat over a stalled sync), and the state-advance test reads $capped, never the post-filter row count. Run with -DryRun to log every send/skip decision and post nothing.
Monitoring note: lastRows: 0 on /api/shopworks-odbc/health is now the NORMAL steady state. Health is reason: fresh + ageMin, not row count. The per-run log line dedupe: N to send, M unchanged is where the real activity shows.

Common jobs

  • Is a sync healthy? From any browser: …/api/shopworks-odbc/health (+ /po-health, /contacts-health, /designs-health, /reps-health) → returns ok, minutes since last success, and the last summary.
  • Run one now: right-click → Run, or schtasks /Run /TN "\NWCA\ShopWorks ODBC Order Sync". Then read its .log.
  • See what happened: the Last Run Result column, or the task's History tab, or the tail of its .log.
  • Change a script's behavior: edit the repo master, copy to the matching C:\NWCA\… path — no task change needed.
  • Thumbnail metadata is automatic: the metadata sync reads the ODBC Thumbnails table directly (joined to DesignLocations for the design id and Des for the design name) — no manual "Thumbnails Report" export needed (retired 2026-07-21).
  • Handy script flags (run manually): -DryRun (validate, 0 writes), -SeedSnapshot (baseline after a bulk import), -CsvOut <path> (emit a CSV for a $0 bulk import).

Never-break rules for this folder

  • Only touch tasks inside \NWCA. Leave the OneDrive / Adobe / Edge / Norton / Windows tasks alone — they're app/OS-managed, get auto-recreated, and deleting them breaks sync/updates/antivirus.
  • New sync? Create it inside \NWCA, run as SYSTEM, script in C:\NWCA\… with its master in the repo bandit-agent/ folder.
  • Never run a large metadata + image batch at the same time (per-second Caspio limit). Bulk loads go through a CSV import, not the API.

How each sync works

  1. Read — the agent opens the FileMaker ODBC DSN (SWODBC, login extro/extro, read-only) and pulls a bounded query (orders/PO/thumbnail-metadata = rows changed since last run; contacts/designs/reps = full scan). Only the thumbnail images come from the file share instead of ODBC.
  2. Join what isn't on the main table — the Order Sync runs a second bounded query for the ship method, which ShopWorks keeps on the address row (Addr.ShipMethod), not on Orders. It fetches the method for just the orders in the delta (chunked id_Order IN (…)) and attaches it as an extra ShipMethod column on ORDER_ODBC — which is what lets the AE data-quality radar flag "a ship method was chosen but no ship-to address was entered". The Thumbnail Metadata Sync works the same way: it resolves each thumbnail's design id and design name by joining Thumbnails → DesignLocations → Des in one bounded query (that design id is the link from a thumbnail to its customer for the portal logo library).
  3. Clean — the agent applies the same normalization the old OneDrive export used (rep names, address/city/state, tiers, flags).
  4. POST — cleaned rows go in chunks to the proxy endpoint above (header x-crm-api-secret). The proxy is the only thing that writes Caspio, upserting by key (ID_Order / ID_PO / ID_Contact / ID_Customer / ID_Design / ID_Serial). It also uploads images to Box.
  5. Heartbeat — every run stamps Sync_Heartbeats so the watchdog can tell "alive but quiet" from "dead".

Each agent supports handy flags: -DryRun (validate + 0 writes), -SeedSnapshot (adopt current state as the delta baseline), -CsvOut <path> (emit a table-shaped CSV for a bulk Caspio import — the import quota, not the API budget).

Big backfills = CSV import, not the API

A Caspio CSV import runs on the Data import/export runs quota (~90/1000), not the metered Integrations API calls (500K/mo). Every agent's -CsvOut mode emits a CSV so a 25k-row backfill costs $0 in API. That's how the full thumbnail backfill was done.

Thumbnails & Box

  • Two parts. Metadata rows (design id, design name, part #, dims) come from a direct ODBC read of the ShopWorks Thumbnails table — scoped to rows that have an image file (FileName IS NOT NULL), joined to DesignLocations for the design id and Des for the design name (ShopWorks ticket 386060 exposed these tables 2026-07-21; the old manual Thumbnails Report*.xlsx export is retired). Images come from the FileMaker container store shared as \\NCA-FS01\Thumbnails (read-only — never write it).
  • All images live on Box (folder ShopWorks Thumbnails Archive, id 400901982283). As of 2026-07-18: 26,896 thumbnails serve from Box, 0 from Caspio. The upload happens on the proxy via uploadFileToBox() using Box creds in the Heroku env — there is no Box client or token on bandit.
  • Transparent to the website. Every consumer resolves the URL as ExternalKey ? /api/files/{key} : FileUrl, so a row that points at Box just serves from Box — no app change needed.

Connecting & troubleshooting

  • Reach bandit from Erik's laptop over PowerShell Remoting: $cred = Import-Clixml "$env:USERPROFILE\bandit-cred.xml"; Invoke-Command -ComputerName bandit -Credential $cred { … } (the credential is DPAPI-encrypted, laptop-bound — re-create it after any domain password change). Or plain RDP.
  • Is a sync healthy? GET /api/shopworks-odbc/health (and /po-health, /contacts-health, /designs-health, /reps-health) return ok + minutes since last success.
  • Logs live next to each script: C:\NWCA\odbc-sync\*.log, C:\NWCA\thumb-image-sync\*.log, C:\NWCA\thumb-sync\*.log. Config for all: C:\NWCA\odbc-sync\config.json (ProxyBase, CrmApiSecret, Dsn).
  • Task inventory: use schtasks /query — the Get-ScheduledTask cmdlet returns empty over PS-remoting on this box.

Vendor rules — OnSite is LIVE production

  • Never blanket-query the ODBC DSN — always WHERE + FETCH FIRST n; unbounded scans can crash OnSite for everyone. No writes ever (order creation stays on the ManageOrders push API).
  • Never poll tightly — minutes apart, not seconds. And never two write-heavy Caspio syncs at once (see the rule at the top).

What this replaced
