### A client-side filter over an unfiltered fetch is a silent-empty waiting to happen (2026-07-26)
- **Problem**: `pages/js/supacolor-job-detail.js:110` built a filtered `q.where` URL into a variable it **never used**; line 114 fetched `/api/transfer-orders?pageSize=500` with **no filter at all** — a full-table read of up to 20 pages / 10,000 rows on EVERY job-detail view — then matched `Supacolor_Order_Number` in JS. The route had no such filter, so a previous author gave up and went client-side, leaving the dead line behind as evidence of the intent.
- **Root Cause**: two failure modes stacked. The quota cost was obvious once measured. The dangerous one was that the client-side filter could only see rows that survived `maxPages`, an unstable `Requested_At DESC` sort (not unique ⇒ Caspio drops/dupes rows across page boundaries), and a `catch` that swallowed **every** error into `return []`. All three degrade to an empty array, and the renderer hid the card when empty — so "the lookup broke" and "this job has no transfers" were **indistinguishable on screen**.
- **Solution**: added an allowlisted `supacolorOrderNumber` filter to `/api/transfer-orders` (escapeSQL like every sibling filter — never a raw `q.where` passthrough); appended `PK_ID DESC` as a tiebreak to that route's sort; the page now throws instead of returning `[]`, and a new `linkedTransfersError` state renders a visible "couldn't load — this job may still have transfers" row. Verified live: job 643778 → ST-260506-0002 in ONE filtered read. 9 tests incl. injection payloads.
- **Prevention**: **if you're filtering client-side, ask why the server can't** — the answer is usually "nobody added the filter", and the cost is a full-table read plus a failure mode that looks like data. Never let `catch → return []` feed a renderer that hides on empty; an error state and an empty state must look different. And a sort column that isn't unique cannot order a multi-page Caspio read.

### The Caspio meter said 4% of limit while Caspio billed 138% — a counter that misses most call paths reads as "we're fine" (2026-07-26, $358 overage)
- **Problem**: invoice AI-334269 billed **178,874 calls over the 500K/period cap** (689.8K used, $0.002/call). A quota audit had shipped 8 days earlier and its follow-up step was "verify via `GET /api/admin/metrics` (`callsByTable`)" — which nobody could act on, because that field **does not exist** and the endpoint reported ~4% of limit.
- **Root Cause**: three independent blind spots, each individually invisible. (a) Only `makeCaspioRequest` + `fetchAllCaspioPages` called `trackCall`, so the **~236 direct-axios call sites across 41 route files** — i.e. every POST/PUT/DELETE — plus `putWithRecordsAffected` and all **four** independent OAuth token caches were never counted. (b) The table name came from `path.split('/').pop().replace('/records','')`; `.pop()` on `/tables/X/records` returns the literal `"records"`, so the entire breakdown collapsed to one row named `records` and per-table attribution had never once worked. (c) The endpoint exposed only `getTopTables(5)`, and the counters are in-memory per-dyno and reset on every cycle — so even the visible number was a fragment.
- **Solution**: metering moved to a **global axios request interceptor** keyed on `*.caspio.com` (`src/utils/api-tracker.js`) — the only counting path, and one a new route cannot bypass by reaching for axios directly. Counts at REQUEST time (Caspio bills 400s and the 400-retry's second request too). Table parsed from the segment after `/tables/`|`/views/`; token fetches labelled `__oauth_token__`; `?full=1` returns the complete breakdown + `processUptimeMs`; endpoint moved behind `requireCrmApiSecret` (it was wide open). 20 tests.
- **Prevention**: **instrument at the transport chokepoint, not at the convenience wrappers** — wrappers get bypassed, an interceptor cannot. A metric that can only under-report is worse than none: it manufactures false confidence. When a runbook says "verify via field X", **run it once and confirm field X exists**. Verified live: `Shopworks_Thumbnail_Report` and `Sanmar_Bulk` were ~25% of calls *each* — half the quota in two tables, completely invisible under the old label.
- **Recurrence, same day, same theme — an EMPTY SOURCE must never render as a healthy value.** Minutes after the `API_Usage_Daily` rollup was switched on, the still-empty table summed to `0` and `/api/admin/usage/alert` reported **"0% of limit"** — "you're fine" — from a meter built specifically to prevent that. A live dyno cannot make zero Caspio calls (the rollup writer itself makes them), so an empty window means *no rows yet*, never *no usage*. Fixed by discriminating on **row count, not the sum** (a window with rows genuinely adding to 0 is still a real 0), and by averaging over **days that have data, not days elapsed** — the rollup went live on day 30 of 30, so dividing one day of calls by 30 under-reported the rate ~30× (690K/period would have read as 98K, 20% of cap). Third instance of this family after `/api/all-brands` caching its own `[]` (2026-07-25): **`0`, `[]`, `{}` and `null` from a data source are "unknown", not "nothing" — reserve a distinct state for "no data" and refuse to judge.** A test asserted the old rule here and still passed; it was checking the right principle against the wrong quantity.
- **FOURTH instance, hours later, in the persistence layer of the same meter**: Caspio billed **15,951** calls that day while the `API_Usage_Daily` row read **1,650**. `tracker.stats.callsByDay` counts since **this process** started, and the rollup PUT that number straight into the row — so each of the day's four dyno restarts (a config set + two deploys) reset the counter and walked the stored total BACKWARDS, keeping only the last process's slice. Fixed by writing a **delta against the stored value** (a fresh process has contributed 0, so restarts become additive), advancing the watermark only after the write lands so a failure is retried, and flushing on **SIGTERM** (Heroku signals before every dyno cycle; without it up to an hour is lost per restart *even with* the delta fix, because those calls were never written at all). **A counter that resets is not a total — anything persisting a since-boot number must accumulate, and the giveaway is always that the error points one way: down.**

### A stub-based UI harness cannot see a missing route — a card 404'd in production for a week while the harness stayed green (2026-07-26)
- **Problem**: `dashboards/js/ae-mission-control.js` fetched `/api/crm-proxy/ae-dashboard/due-dates`, which **`server.js` never registered**. `git log -S` showed it added in `df1b62d4` and removed by the `aa33b66f` "revert foreign vendor-portal server.js hunks" hotfix — the same revert ate `data-quality`, which someone noticed and restored; this one nobody did. Both reps saw "Order due dates failed to load (HTTP 404)" every day.
- **Root Cause**: `tests/ui/test-ae-mission-control-stub.js` replaces `window.fetch` **wholesale** and answers that URL itself, so the harness renders the card perfectly whether or not the route exists. It is structurally incapable of detecting an unregistered endpoint, a changed response shape or a broken auth gate.
- **Solution**: registered the forwarder; added a header comment to the stub stating it is a **RENDER harness, never a CONTRACT harness**; probe registration live instead — `curl -o /dev/null -w '%{http_code}' localhost:3000/api/crm-proxy/...` where **401 = registered = pass, 404 = not registered**, cross-checked against a deliberately fake route so the probe is proven to discriminate. Route census: `grep -c "app.get('/api/crm-proxy/ae-dashboard/" server.js` vs `grep -o "/api/crm-proxy/[a-z0-9/-]*" <page>.js | sort -u`.
- **Prevention**: **a mock that stands in for the network can never test the network.** Any page whose harness stubs fetch needs a separate one-line live probe per route, and the route inventory comment at the top of `server.js` must list every forwarder a page calls (a revert that drops one is otherwise invisible). Also: `?as=rep` now stubs a NON-admin session — the harness had only ever stubbed Erik-as-admin, so the experience that actually ships to the reps, including everything deliberately suppressed during view-as, had never once been exercised.

### `requestAnimationFrame` is throttled to ZERO in a background tab — an animated counter left the bonus reading $0 (2026-07-26)
- **Problem**: a new count-up animated the Q3 bonus from a `$0` placeholder to its real value on rAF. Opened in a background tab (middle-click from the staff dashboard, or a restored multi-tab session) **not one frame ever fires**, so the hero sat at **$0 indefinitely** — a rep being told her bonus is zero.
- **Root Cause**: the animation owned the only write to the element. `document.hidden` suspends rAF entirely; the fallback path checked `prefers-reduced-motion` but not visibility.
- **Solution**: **paint the true value first, then decide whether to decorate it** — `paint(to); if (state.reduceMotion || document.hidden || !to) return;` before scheduling any frames. A frozen rAF can now only cost the animation, never the number.
- **Prevention**: never let an animation be the sole writer of a real value; render truth synchronously and treat motion as an enhancement. And `prefers-reduced-motion` is a CSS-only signal — a rAF counter and a canvas confetti are invisible to `@media`, so they need an explicit `matchMedia` check in JS as well.

### Per-item escaping in a list builder: three of five branches escaped, two didn't (2026-07-26)
- **Problem**: a new "next best action" card assembled candidates from five sources and interpolated each into `innerHTML`. Three builders called `esc()` on the company name and two did not, so the harness's `Harbor Electric <b>xss</b>` fixture rendered as **live markup** (ShopWorks company names and lead-form input are external data).
- **Solution**: candidate builders now hold **raw** strings and escaping happens **once at the single render site**. One place to get right instead of five places to forget.
- **Prevention**: when N producers feed one `innerHTML` sink, escape at the **sink**, never per producer — "every caller remembers to escape" is not a property a codebase can hold. Keep an XSS probe fixture (a literal `<b>` in a name) in every list harness; it is what caught this.

### One shared `OverlapMinutes` across syncs with DIFFERENT cadences is a silent-data-loss trap (2026-07-26)
- **Problem**: bandit's ODBC Order/PO syncs run every **15** min against a shared `OverlapMinutes: 30`, and `shopworks-odbc-sync.js` PUTs **unconditionally** — so every changed row landed in 3 consecutive runs and was written to Caspio ~3×. The obvious fix (drop the shared key to 20) would have caused **silent data loss**: the same key is read by `sync-thumbnail-metadata.ps1`, which runs on a **30-minute** cadence — an overlap below its own cadence opens a window in which modified rows are never seen again.
- **Root Cause**: one config value expressing a constraint that is **per-task** (it must exceed *that task's* cadence), shared by four scripts whose cadences range 15 min → 12 h. Nothing in the config or the scripts recorded the coupling, so the value looked like a global tuning knob.
- **Solution**: Order/PO now read their own `OrdersOverlapMinutes` (default **20** → 2 runs, a third fewer writes) and deliberately do NOT fall back to the shared key; thumbnail-metadata keeps 30 and gained a `ThumbMetaOverlapMinutes` override. The coupling is documented in all three scripts and on `/dashboards/bandit-integration.html`.
- **Prevention**: **overlap must always exceed (cadence + run duration + clock skew)** — write that next to the value, not in a commit message. A config key shared by jobs with different schedules needs either per-job keys or a derivation from each job's own cadence. Related trap found the same day: the Supacolor health watchdog flagged "stale" at 25 min, so moving that sync to a 30-min cadence would have fired a false alert every cycle — a cadence change must be checked against every freshness threshold that watches it.

### Four hand-maintained brand lists drifted until a top-seller search returned ZERO products (2026-07-25)
- **Problem**: brand data lived in 4 copies — `BRAND_LANDING_PAGES` (brands-flyout), `BRAND_KEYWORDS` (product-search-service), the drawer's static `/custom-*` links, `PRIORITY_BRANDS` (brands.js). They disagreed silently. `'bella canvas'` mapped to `'Bella+Canvas'` while the catalog spells it **`'Bella + Canvas'`** — verified live, `brand=Bella+Canvas` returns **0 products**, so searching one of our best sellers showed customers an empty page. Same shape for `'stanley'` (catalog: `Stanley/Stella`), plus adidas/Under Armour/Columbia/Patagonia/YETI which SanMar doesn't carry at all — each applied a filter for a brand with no products instead of falling back to text search. Separately, Sport-Tek/District/CornerStone/Eddie Bauer/TravisMathew had landing pages but no keyword, and `/brands.html` sent all 46 tiles to the generic catalog filter.
- **Root Cause**: the same fact (a brand's canonical name) was **typed by hand in four places**. Every copy was individually plausible, so nothing looked wrong in review; only comparing a copy against the *catalog's actual spellings* exposed it — and nothing ever did that.
- **Solution**: `shared_components/js/brands-registry.js` is the one source. The load-bearing idea is **derive, don't duplicate**: search keywords are GENERATED from `CATALOG_BRANDS` (the 46 verified `/api/all-brands` spellings), so a keyword *cannot* name a brand that doesn't exist. Consumers read from it; the drawer stays static HTML (crawlable links) and is asserted against the registry by the test instead of being generated. 16 tests, verified to fail when drift is reintroduced.
- **Prevention**: **when the same fact appears in 2+ files, derive the copies from one source or add a test that compares them — a convention that they "should match" is not a mechanism.** Validate identifiers against the system that owns them (here: the catalog), not against another copy. Two traps if you build a keyword matcher on `query.includes(kw)`: keywords must be **≥3 chars** (`'pa'` turned "pants"/"apparel" into Port Authority; `'pc'` turned style **PC61** into a brand filter) and **ordered longest-first** (else `ogio` shadows `ogio endurance`). Enumerate ordinary non-brand queries in a test that asserts they resolve to NOTHING.

### A truthy `[]` pinned an EMPTY brand list for 24h server-side + 6h in every browser — homepage Brands menu went blank (2026-07-25)
- **Problem**: the homepage Brands mega-dropdown rendered "No brands available". `/api/all-brands` was healthy when checked (200, 46 brands, 0 broken logos) and a fresh browser was fine — but Erik's browser stayed broken, which is the tell.
- **Root Cause**: `/api/all-brands` **cached its own empty result**. The guard was `if (!allBrandsCache.data || …)` over a plain `{at, data}` object, and **`[]` is truthy in JS** — so one bad Caspio read (stale token / `maxPages` truncation / transient failure) stored an empty array and served it for **24h** from the dyno, shipped with `Cache-Control: public, max-age=21600` which froze "no brands" into **every visitor's browser for 6h with no revalidation**. Three aggravators: `catch` never fired so nothing logged an error (it looked like success); `/api/product-cache/clear` couldn't flush it (a plain object, not in the `createTtlCache` registry) so only a dyno restart worked; and the front end **dead-ended** on empty instead of degrading. `/api/all-categories` carried the identical copy-pasted bug.
- **Solution**: proxy — moved both routes onto `createTtlCache` (registry membership ⇒ `/product-cache/clear` + `?refresh=true` both work), `set()` only when `length > 0`, and an empty read now returns **503 + `Cache-Control: no-store`** (never a cacheable empty 200) so the next request retries. `max-age` 21600→600 + `stale-while-revalidate`. Front end — a static `FEATURED_BRANDS` tier (the 15 `/custom-<brand>` landing-page brands) paints on init with **zero network dependency** and is the fallback for empty/503/offline, so the menu is structurally incapable of rendering blank; layered static tier → CDN logo → 🏷️ glyph. 12-test `all-brands-empty-cache-guard.test.js` locks it, including "an empty read cannot overwrite an already-good cached list".
- **Prevention**: **never cache an empty collection** — `if (!cache.data)` does NOT catch `[]`; guard on `.length`. Never pair a long `max-age` with a cache that has no flush path: a long TTL turns a one-minute upstream blip into a multi-hour outage you can't clear. An empty upstream result is a FAILURE (503/no-store), not a cacheable success. And for nav/chrome that's editorial and rarely changes, prefer a static list with an API-driven long tail — a menu should never be able to go blank because a backend hiccuped. Diagnostic tell: server healthy + fresh browser fine + one browser broken ⇒ suspect a cached bad response, not the code.

### The INVERSE miss: a prefix gate covers ONE mount, not the router — `/api/order-odbc` + `/api/order-dashboard` + `/api/customers` stayed anonymous 3 weeks after the `/api/orders` "full-gate" (2026-07-18, proxy v951)

And "the router is gated" claims must be proven by curling each ROUTE, not the mount.
